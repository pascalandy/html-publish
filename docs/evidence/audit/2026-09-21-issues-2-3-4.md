### Baseline departures from contract ownership

At commit 89f078e, `pyproject.toml` exports `html-publish-server`, `html-publish-remote`, and
`html-publish-deploy`. The installer in `html_publish/deploy.py` starts `html_publish.server` as
the persistent HTTP backend. The [README](../../../README.md) and the
[controlled operations guide](../../operations.md) document the remote client and installer as
the operating route.

The core transaction ownership still matches the contract. `html_publish/store.py` owns archive
and activation mutations, and `html_publish/cli.py` owns CLI arguments, JSON, and exit codes. The
delivery and installation owners do not match S1, S8, and S10. Those sections place HTTP delivery
in native Serve or a verified Caddy alternative, prohibit a remote adapter or daemon, and exclude
a persistent publisher. A later architecture decision must reconcile the implementation and the
target contract. Adding tests does not resolve this departure. This audit does not classify the
existing controlled deployment as a finished-product defect or remove its tools.

## What remains, by owner

This repository can close the missing content-identity case and many core and guard gaps with
focused tests. The runtime Git version check and configured-limit echo require implementation
changes. Reconciling the server, remote client, and installer with the contract requires a
separate architecture decision. Live hosting gaps remain outside local test coverage.

These need access outside this environment and keep issue #2 open:

- An authorized isolated direct Tailscale file-serving test. If it fails the required freshness
  cases, prove one loopback Caddy alternative with the same cases.
- `If-None-Match` replay, Unicode, space, percent, mount-boundary, deleted-asset, and
  file/directory-transition rows in the hosting probe.
- A reusable probe script under `docs/evidence/hosting/`.
- Browser observations for the freshness rows, a second tailnet device, and re-verification of
  the recorded atomic-selection and cleanup rows.

All of those belong to the next operator session on `om1`. Until then, issue #2 stays open and
this MVP is not production-ready.
